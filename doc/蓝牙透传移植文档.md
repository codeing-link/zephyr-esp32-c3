# 蓝牙透传代码移植文档

本工程将 AT 协议逻辑与 ESP32-C3/Zephyr 硬件适配分离。移植时应保留协议层，替换 BLE、UART、非易失存储和复位等平台实现。当前协议层可作为独立的标准 C 模块编译，不包含 Zephyr 或芯片 SDK 头文件。

## 1. 当前可移植性结论

当前实现的可移植性良好，适合移植到使用其他 RTOS、裸机 SDK 或不同 BLE 控制器的平台：

- AT 语法、参数校验、应答文本与透传路由均在 `ttm_protocol.*` 中，未混入 GATT、NVS、GPIO 或 Zephyr API。
- `struct ttm_protocol` 是显式实例，不再使用全局协议状态；一个测试程序或产品程序可各自创建独立实例。
- `struct ttm_port` 的全部回调都带有 `void *context`。目标平台可将自己的设备对象、连接对象或驱动句柄放入此字段，而不需要使用静态全局变量。
- `src/main.c` 仍是 ESP32-C3 的应用入口和适配示例，其中包含 GPIO8 状态灯、Zephyr GATT、UART 中断和 Settings/NVS。这些均应由目标平台替换，不属于协议核心。

当前不建议为了拆分文件而继续细分协议核心：AT 命令之间共享同一份配置和一致的回显/应答规则，维持为一个无平台依赖的模块更易审查和移植。

## 2. 代码分层

|层级|文件|职责|移植处理|
|---|---|---|---|
|协议核心|`src/ttm_protocol.c`、`src/ttm_protocol.h`|解析 `TTM:` 指令、校验参数、生成回复、选择 UART/BLE 转发|原样复用，不依赖 Zephyr 头文件|
|平台适配|`src/main.c`|GATT、广播、UART 中断、工作队列、GPIO8、NVS、复位|按目标 RTOS/SDK 重写回调实现|
|平台配置|`prj.conf`、overlay、分区配置|BLE 缓冲、MTU、UART 引脚、NVS 分区|按芯片及 SDK 配置|

协议层通过 `struct ttm_port` 请求平台执行动作。初始化时由调用方提供协议实例、配置和端口表：

```c
struct ttm_protocol protocol;
struct ttm_config config;
struct ttm_port port = {
    .context = platform_context,
    .uart_send = platform_uart_send,
    /* 其余平台回调 */
};

ttm_protocol_init(&protocol, &config, &port);
```

不要在 `ttm_protocol.*` 中加入 SDK 头文件、GATT 类型或 Flash API，也不要恢复为全局单例，这样同一协议文件可用于其他蓝牙芯片及宿主机单元测试。

## 3. 必须实现的平台回调

目标平台需为 `struct ttm_port` 提供等价能力。每个回调的第一个参数都是 `context`，即初始化时填写的 `port.context`；可用于取得平台私有状态。

|能力|用途|实现要点|
|---|---|---|
|UART 发送|AT 回显、结果和 BLE 下行数据|保证缓冲区在发送完成前有效；避免在 BLE 中断中长时间阻塞|
|BLE 通知|UART0→`FFF4`|仅在已连接且已订阅时发送；按协商 MTU 分片|
|连接状态|限制 AT 设置并处理 `CIT`|连接、断开时及时更新状态|
|串口改波特率|`BPS`|必须先以旧波特率发送 `TTM:OK`，再生效|
|广播重启|名称、PID、ADP、ADD 等修改后刷新广播|先停止或等待旧广播释放，再按新参数启动|
|连接参数更新|`CIT`|仅连接状态调用平台连接参数接口|
|配置存取|掉电保持参数|使用 KV、Flash 或 NVS；需要版本与长度校验|
|身份地址与复位|`MAC`、`RST`|自定义 MAC 应在 BLE 协议栈初始化前生效，设置后复位|

## 4. BLE GATT 与数据路径

必须建立一个主服务和两个特征：

|对象|UUID|属性|数据方向|
|---|---|---|---|
|主服务|`0xFFF0`|Primary Service|—|
|串口写入特征|`0xFFF3`|Write、Write Without Response、Prepare Write|BLE 中央→UART0|
|串口通知特征|`0xFFF4`|Notify|UART0→BLE 中央|

`FFF3` 不应只支持一次性短写。macOS 对 150 字节数据会使用 Prepare/Execute 长写，因此平台适配层必须将准备写阶段缓存或交给协议栈处理，并在 Execute 后按正确顺序转发完整数据。UART 接收数据应放入队列或工作线程后再通知 BLE，避免在中断上下文直接调用协议栈。

## 5. MTU、缓冲区和分包

- 默认 ATT MTU 为 23，未协商时有效载荷为 `MTU - 3 = 20` 字节。
- 必须允许中央设备协商到 MTU 153，对应 150 字节有效载荷。
- BLE→UART 路径至少要容纳 150 字节；本工程 UART 数据缓冲为 160 字节。
- UART→BLE 路径必须按当前协商 MTU 减 3 分片，不能假设手机必定完成 MTU 交换。
- 控制器 ACL 包数、主机 TX 上下文和 ATT Prepare Write 数量应相匹配，否则可能出现启动告警、写入失败或内存耗尽。

## 6. 参数保存和兼容升级

需要保存的数据包括：数据延时、广播周期、产品 ID、名称、自定义 MAC 和附加广播数据。建议保存结构加入魔数、版本号、长度和校验字段。读取失败、版本不兼容或长度异常时，应使用出厂默认值，并删除旧记录后在下一次正常设置时写入新格式。

自定义 MAC 是 BLE 身份地址，通常无法在蓝牙栈已经启用后安全切换。因此 `TTM:MAC-xxxxxxxxxxxx` 成功后应提示或执行复位，复位前继续使用旧地址是可预期行为。

## 7. 与硬件相关的差异

- `CDL` 依赖 BCTS：原始协议要求先拉低 BCTS，延时后再从 TX 发送。ESP32-C3 开发板未接该引脚，当前仅保存和解析该参数；移植到带 BCTS 的硬件时必须补齐时序。
- `TPL` 依赖控制器厂商 API：当前 ESP32-C3 控制器不支持运行时功率切换，协议层仍返回成功以保持 AT 兼容性。目标平台应接入真实的 TX 功率接口，并在射频仪表上验证。
- GPIO8 闪灯仅是本开发板健康指示，不属于透传协议；移植时可改为目标板的 LED 或删除。

## 8. 移植检查清单

1. 编译 `ttm_protocol.*`，并实现全部 `ttm_port` 平台回调。
2. 建立 `FFF0/FFF3/FFF4` 服务，验证读写权限、通知订阅和长写。
3. 配置 UART 默认 115200、8N1，验证 AT 回显后返回结果的顺序。
4. 配置默认 MTU 23、最大 MTU 153，并分别验证 20 字节及 150 字节 BLE→UART。
5. 实现参数持久化、旧版本配置保护及重启后的参数恢复。
6. 验证广播名称、产品 ID、广播周期和附加数据在修改后立即刷新。
7. 运行 UART AT 自动测试、手机 BLE 测试和 macOS/目标平台等价闭环测试。
